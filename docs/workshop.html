Take an existing large-scale spatial product, fold in regional ground observations and high-resolution covariates, and produce a defensible regional posterior map — with an honest answer to whether it's precise enough to manage by.

The big picture

Seventeen steps, but one shape: characterize what you already believe, confront it with new evidence, update it, and check whether the result is good enough to act on. Everything below is a zoomed-in view of one node in this pipeline.

Numbering note This overview uses one number per pipeline stage. The step-by-step walkthrough that follows is more granular — it splits "Bayesian update" into the update itself, the spatial application, the posterior export, the change-of-support check, and the precision test — so its numbers run 0 through 16. Both describe the same pipeline at different zoom levels.
STEP 00

What do we know?

Before any modelling: what information already exists, and what does each piece actually represent?

Build one inventory that covers everything — raster maps, uncertainty rasters, ground observations, soil cores, vector layers, ecosystem classifications, remote-sensing products, management boundaries, existing model outputs, ancillary data. The point isn't the list; it's that every dataset gets forced into the same table, with the same five columns, so nothing enters the workflow with unstated assumptions.

Required table — one row per dataset

No mean/uncertainty available? Write NA or "not applicable" — never leave the cell blank, and never invent a number.

Why spatial support gets its own column A 250-m raster cell and a soil core are not the same kind of observation. Writing the support down forces the question what area does this one piece of information actually represent? before that assumption gets buried three modelling steps downstream.

For each dataset in your project, write down by hand:

  1. What does it measure?
  2. What is its estimate?
  3. What is its uncertainty?
  4. How was that uncertainty generated?
  5. What spatial area does one observation represent?

Don't proceed to Step 1 until this table exists on paper for your real datasets.

STEP 01

Characterize the prior over the AOI

What does the existing map tell us about our region?

Two rasters come in: prior_mean.tif and prior_sd.tif. Both get summarized over the AOI — but the two summaries mean different things, and conflating them is the single most common mistake in this step.

1a — the estimate

AOI mean
x̄AOI = 1n Σᵢ xi

Five pixels inside the AOI:

x = 120, 140, 150, 160, 180 x̄ = (120+140+150+160+180) / 5 = 150

Mean prior estimate = 150 Mg C/ha. Straightforward.

1b — what the uncertainty raster is not

Averaging the per-pixel SD raster gives the typical uncertainty of one pixel — a useful, honest number. It is not the uncertainty of the AOI-wide mean.

Five pixel SDs:

SD = 20, 25, 30, 25, 20 mean(SD) = 24

Report: "typical pixel uncertainty = 24 Mg C/ha."
Do not report: "AOI uncertainty = 24 Mg C/ha." Those are different claims.

1c — the (tempting, incomplete) formula for the mean's uncertainty

If pixel errors were independent
Var(x̄) = 1n² Σᵢ σᵢ²  →  SDx̄ = √( Σσᵢ² / n² )
Why we don't use this yet Nearby pixels have correlated errors — they came from the same underlying model with the same biases. Treating them as independent will understate the true uncertainty of the AOI mean whenever spatial autocorrelation is real, which for a carbon prior it usually is.

Version 1 rule

Report two separate, clearly-labelled numbers and stop there:

  • AOI estimate — x̄
  • Mean pixel-level SD within AOI — mean(SD), explicitly labelled as such

If management eventually needs a formal AOI-total uncertainty, that's where spatial covariance or posterior simulation gets added later — not now.

characterize_prior <- function(prior_mean, prior_sd, aoi) {
  library(terra)
  pm <- mask(crop(prior_mean, aoi), aoi)
  ps <- mask(crop(prior_sd, aoi), aoi)

  list(
    aoi_mean_estimate    = as.numeric(global(pm, "mean", na.rm = TRUE)),
    mean_pixel_sd_in_aoi = as.numeric(global(ps, "mean", na.rm = TRUE))
  )
}

STEP 02

Process and harmonize the ground data

What did we actually measure in the field, and how do we turn it into the variable we want to map?

Chain of transformations
Field measurements → Carbon calculation → Depth harmonization → Final response variable

Target depths for this project: 0–15, 15–30, 30–50, 50–100 cm.

2a — one core, by hand, first

Stock for one layer
SOCstock = SOCconc × BulkDensity × Depth × (1 − CF) CF = coarse-fragment fraction. Make every unit conversion visible — this is exactly what the spreadsheet is for.

One layer:

SOC concentration = 20 g/kg = 0.020 g SOC per g soil bulk density = 1.2 g/cm³ thickness = 15 cm → 15 cm × 10 000 cm²/m² = 150 000 cm³ per m² column coarse fragments = 0 (ignore CF term) mass of soil in column = 1.2 g/cm³ × 150 000 cm³ = 180 000 g/m² SOC mass = 0.020 × 180 000 g/m² = 3 600 g/m² = 3.6 kg/m² convert to Mg/ha (×10) = 36 Mg C/ha for this one 15 cm layer

Work through one complete core by hand before writing any code — the spreadsheet should make every unit conversion visible so the R output can be checked against it line by line.

2b — harmonizing to target depths

Field intervals rarely line up with modelling intervals. Where a target interval overlaps two measured layers, split each contributing stock proportionally to how much of the target interval it covers:

Overlap-weighted stock
Stocktarget = Stock₁ × overlap₁depth₁ + Stock₂ × overlap₂depth₂

Target 0–15 needs: all of measured 0–10, plus the top 5 cm of measured 10–25 (a 15 cm layer, so 5/15 of its stock).

Stock(0–10) = 24 Mg C/ha (full layer, full overlap) Stock(10–25) = 33 Mg C/ha, overlap with 0–15 target = 5 of 15 cm Stock(0–15) = 24 × (10/10) + 33 × (5/15) = 24 + 11 = 35 Mg C/ha

Which R package?

PackageFit for this step
aqpStrong general soil-profile framework (SoilProfileCollection). aqp::harmonize() is for denormalizing profile-level structures, not a depth-interpolation tool — use it if you want a structured profile data system alongside step 2, not as the harmonizer itself.
soilassessmentRecommended. depthharm() takes observed intervals and returns properties at specified target intervals — directly the task at hand.
iTHiRBuilt for spectroscopy / infrared workflows. Not the default for plain depth harmonization.

Version 1: spreadsheet → soilassessment::depthharm(), checked against the hand calculation above before it's trusted.

# base R is preferable to a package here — the calculation is this simple
compare_prior_observed <- function(field) {
  field$residual   <- field$observed - field$prior
  field$z_residual <- field$residual / field$prior_sd

  list(
    field = field,
    bias  = mean(field$residual),
    mae   = mean(abs(field$residual)),
    rmse  = sqrt(mean(field$residual^2))
  )
}

STEP 05

Spatial residual analysis

Where is the prior wrong?

Start extremely simple: plot the residuals in space, then look at them against latitude, longitude, land cover, NDVI, elevation. Only then, if there's visible structure, reach for Moran's I (spdep) or a variogram (gstat).

Do not interpolate the residuals in Version 1 Kriging the residuals now would hide exactly the observations we most need to look at directly. gstat also does point and block kriging, which is the eventual path to support-aware modelling — but that's a later version, once the raw pattern has actually been seen.
▸R Plot residuals, optionally test for spatial structure R/step05_spatial_residuals.R
R/step05_spatial_residuals.R
spatial_residual_diagnostics <- function(field_sf, run_moran = FALSE, run_variogram = FALSE) {
  library(ggplot2)
  p <- ggplot(field_sf) +
    geom_sf(aes(colour = residual)) +
    scale_colour_gradient2(low = "#2F5233", mid = "grey90", high = "#93392A")

  out <- list(plot = p)

  if (run_moran) {
    library(spdep)
    nb <- knn2nb(knearneigh(sf::st_coordinates(field_sf), k = 4))
    lw <- nb2listw(nb)
    out$moran <- moran.test(field_sf$residual, lw)
  }
  if (run_variogram) {
    library(gstat)
    out$variogram <- variogram(residual ~ 1, data = field_sf)
  }
  out
}

build_rf_workflow <- function(formula, data) {
  library(tidymodels)

  rf_model <- rand_forest(trees = 500, mtry = tune(), min_n = tune()) |>
    set_mode("regression") |>
    set_engine("ranger")

  rf_recipe <- recipe(formula, data = data)

  workflow() |>
    add_recipe(rf_recipe) |>
    add_model(rf_model)
}

STEP 09

Bayesian update

Given what we knew before and what the regional evidence tells us, what should our updated estimate be?

The first genuinely Bayesian step. For Version 1: the Normal–Normal update — precision-weighted averaging of a prior and a piece of evidence, each described by a mean and an SD.

Posterior mean
μpost = μp/σp²  +  μr/σr²1/σp²  +  1/σr²
Posterior variance
σpost² = 11/σp²  +  1/σr² Each source contributes in proportion to its precision (1/variance) — the more confident source pulls the posterior harder toward itself.

Prior: 150 ± 30. Regional estimate: 170 ± 20.

prior precision = 1 / 30² = 0.001111 regional precision = 1 / 20² = 0.002500 μ_post = (150 × 0.001111 + 170 × 0.002500) / (0.001111 + 0.002500) = (0.1667 + 0.4250) / 0.003611 = ≈ 164 σ_post² = 1 / 0.003611 = 276.9 σ_post = √276.9 = ≈ 16.6
Prior150 ± 30
Regional170 ± 20
Posterior164 ± 17

The posterior sits closer to the regional estimate than to the prior, because the regional evidence is more precise (smaller SD).

▸R The scalar update, checked against the worked example R/step09_bayesian_update.R
R/step09_bayesian_update.R
bayesian_update_normal <- function(prior_mean, prior_sd, evidence_mean, evidence_sd) {
  prior_precision     <- 1 / prior_sd^2
  evidence_precision  <- 1 / evidence_sd^2
  posterior_precision <- prior_precision + evidence_precision
  posterior_variance  <- 1 / posterior_precision

  posterior_mean <- posterior_variance *
    (prior_mean * prior_precision + evidence_mean * evidence_precision)

  list(
    posterior_mean = posterior_mean,
    posterior_sd   = sqrt(posterior_variance)
  )
}

STEP 10

Apply the update spatially

The same equations, at every pixel.

For every 10-m cell: prior mean + prior SD, regional prediction + regional uncertainty, in → posterior mean + posterior SD, out. Nothing new mathematically — the win here is that terra raster algebra runs the exact scalar equations from Step 9 across an entire grid at once.

▸R The same formula, as raster algebra R/step10_bayesian_update_raster.R
R/step10_bayesian_update_raster.R
bayesian_update_raster <- function(prior_mean, prior_sd, regional_mean, regional_sd) {
  library(terra)

  posterior_variance <- 1 / (1 / prior_sd^2 + 1 / regional_sd^2)
  posterior_sd        <- sqrt(posterior_variance)
  posterior_mean       <- posterior_variance *
    (prior_mean / prior_sd^2 + regional_mean / regional_sd^2)

  c(posterior_mean = posterior_mean, posterior_sd = posterior_sd)
}

STEP 11

Create the posterior map

What do we ship?

posterior_mean_10m.tif, posterior_sd_10m.tif, posterior_cv_10m.tif — and, if useful, 95% bounds.

Remember The 10-m map contains genuine inferred fine-scale variation — it is not a resampled version of the 250-m prior. The high-resolution detail comes from the regional covariates and ground observations, not from the coarse prior.
▸R Export the posterior products R/step11_export_posterior.R
R/step11_export_posterior.R
export_posterior_products <- function(posterior_mean, posterior_sd, outdir) {
  library(terra)
  dir.create(outdir, showWarnings = FALSE, recursive = TRUE)

  posterior_cv <- posterior_sd / posterior_mean
  lower95 <- posterior_mean - 1.96 * posterior_sd
  upper95 <- posterior_mean + 1.96 * posterior_sd

  writeRaster(posterior_mean, file.path(outdir, "posterior_mean_10m.tif"),    overwrite = TRUE)
  writeRaster(posterior_sd,   file.path(outdir, "posterior_sd_10m.tif"),      overwrite = TRUE)
  writeRaster(posterior_cv,   file.path(outdir, "posterior_cv_10m.tif"),      overwrite = TRUE)
  writeRaster(lower95,        file.path(outdir, "posterior_lower95_10m.tif"), overwrite = TRUE)
  writeRaster(upper95,        file.path(outdir, "posterior_upper95_10m.tif"), overwrite = TRUE)

  invisible(list(mean = posterior_mean, sd = posterior_sd, cv = posterior_cv))
}

check_change_of_support <- function(posterior_mean_fine, prior_mean_coarse) {
  library(terra)
  posterior_aggregated <- resample(posterior_mean_fine, prior_mean_coarse, method = "average")
  diff <- posterior_aggregated - prior_mean_coarse

  list(
    posterior_aggregated = posterior_aggregated,
    difference      = diff,
    mean_difference = as.numeric(global(diff, "mean", na.rm = TRUE))
  )
}

compare_prior_posterior_maps <- function(prior_mean, posterior_mean, prior_sd, posterior_sd) {
  delta_mu <- posterior_mean - prior_mean
  uncertainty_reduction <- 1 - (posterior_sd / prior_sd)
  c(delta_mu = delta_mu, uncertainty_reduction = uncertainty_reduction)

STEP 14

Don't implement the advanced Bayesian model yet

Not now — but what does "later" actually look like?

The Normal-Normal update in Steps 9–10 is enough to demonstrate the concept and ship a defensible Version 1. A future hierarchical spatial Bayesian model — brms, INLA, or inlabru — would do something genuinely more powerful: model spatial autocorrelation, observation error, prior uncertainty, covariates, spatial random effects, prediction uncertainty, and different spatial supports all at once, rather than pixel-by-pixel.

Version 1 = simple Bayesian updating. Version 2 = spatial/hierarchical Bayesian model, if the project warrants it. No code in this step — it's a roadmap marker, not a task.

# Start simple: rank candidate cells by posterior SD (+ optional |z-residual|),
# return the coordinates of the top n. This is the seed for a proper
# space-filling / value-of-information design later.
propose_next_sample_sites <- function(posterior_sd, z_residual = NULL, n = 10) {
  library(terra)
  score <- posterior_sd
  if (!is.null(z_residual)) {
    score <- score + abs(resample(z_residual, posterior_sd))
  }
  top_cells <- which(rank(-values(score), na.last = "keep") <= n)
  xyFromCell(score, top_cells)
}

From scripts to a targets pipeline

Every step above is deliberately one function in R/, run once by one script in scripts/. That's not a limitation — it's the interface targets expects.

Once every step's script runs cleanly stand-alone, wiring them into a pipeline is mechanical: tar_source("R") loads every function, and each pipeline node becomes one tar_target() call — the exact function call that used to live in scripts/run_XX_*.R, now with its inputs and outputs tracked so targets only reruns what actually changed.

Why this order of operations matters Write and hand-verify the function first, run it once from a disposable script second, wire it into _targets.R third. Debugging a broken pipeline node inside tar_make() is much harder than debugging a plain function call at the console — the scripts in scripts/ stay useful afterward as the fastest way to test one step in isolation.
